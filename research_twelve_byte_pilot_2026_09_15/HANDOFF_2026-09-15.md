## 1. What the system is

Per question, from that question's own archive text:

```
Z = hstack([ LSA32(word-TFIDF, seed 5101), word-TFIDF, char-TFIDF ])     ~10^5 columns
Y = normalize( TruncatedSVD(96, random_state=5204).fit_transform(Z) )
C = Y - mean(Y)
SIGN96 = (C >= 0)                                              96 bits = 12 B
```

There is **no neural embedding and no pretrained model anywhere**; the
protocol forbids them for the frozen tasks. The fit is **per question** by
design, not a defect. One indexed unit = one conversation turn,
`[date] role: content`; gold is a turn flagged `has_answer`.

Archives: LME 470 archives / 231,606 docs; PerLTQA 30 / 12,288;
RealTalk 10 / 8,944.

## 2. The metric that was missing

The programme measured expected fractional R@3. The session added **hit@k** —
"did at least one gold document land in the top k" — under the same
uniform-random-within-tie convention the frozen `exact_frac` uses. A `22.9 %`
figure circulating as "SIGN96 hit@10" is **not that**: it is standardized
float's FR@3 on RealTalk. The real starting point:

| arm | bytes/doc | PerLTQA | LME | RealTalk |
|---|---|---|---|---|
| SIGN96 (`sym`, Hamming) | 12 | 75.76 | **86.08** | 46.68 |
| asymmetric (`asym`) | 12 | 80.19 | 85.74 | 43.55 |
| B8 | 12 | 80.12 | 85.11 | 41.56 |
| sign88 (drop-only) | 11 | 79.56 | 85.32 | 42.27 |
| float96 (uncentered ref) | 768 | 80.81 | 82.55 | 36.60 |
| float_std (standardized) | 768 | **83.96** | **88.30** | **48.51** |

## 3. Five doors, measured shut

**a. More bytes.** 12 B -> 768 B buys +2.2 pp on LME and +1.8 pp (ns) on
RealTalk. Only PerLTQA shows a real gain (+8.2 pp).

**b. Better bit allocation.** At hit@10, `b8 - sign88` is statistically zero
on all three (PerLTQA +0.56 [-0.01, 1.15]). `asym - sym` is +4.43 pp on
PerLTQA but -0.33 and -3.13 elsewhere: benchmark-divergent, never pool.

**c. Different retrieval unit.** Sentence / 2-sentence / turn / turn+prev /
session, compared at equal **characters of text shown** (not "top-10 units",
which is meaningless across unit sizes). At a 4,000-character budget:
turn 70.8 %, sentence 68.8 % — and sentence costs **82,624 B of storage vs
5,947 B**, i.e. 14x more for nothing. On the strict measure (whole gold turn
covered) turn wins 70.8 vs 12.5. **The production unit is already optimal.**

**d. More dimensions.** Z (no projection, ~10^5 columns) vs SVD96, 180 LME
questions, paired: `Z - svd96 = +3.89 pp [1.06, 6.72]` for the float arm, and
`Z - svd384 = -0.56 pp [-1.65, 0.53]` — i.e. **384 dimensions already capture
everything the full feature space has.** But the production arm is the *sign*
arm, and SIGN96 at 12 bytes scores 86.08 against Z's 86.1: for the deployed
scorer there is no projection bottleneck at hit@10 at all.

**e. Compressing the 12 bytes.** First-order entropy is **95.7 of 96 bits** —
the pipeline's orthogonalization plus mean-centering has already whitened
them. Best lossless gain: LME 11 %, PerLTQA 5 %, RealTalk **negative**.
Per-code compression inflates by 2.7x (gzip header on 12 bytes).
Similarity-ordering loses: the permutation costs more than it saves.

## 4. What did work

**Deleting bits, not compressing them.** Random noise is both incompressible
*and* useless; the two facts are consistent. With the frozen variance
ordering:

| bits | bytes | LME hit@10 | delta vs 96 |
|---|---|---|---|
| 96 | 12 | 86.08 | — |
| 88 | 11 | 85.80 | -0.28 ns |
| **80** | **10** | **84.97** | **-1.11 ns** |
| 72 | 9 | 84.27 | -1.81 * |
| 48 | 6 | 79.17 | -6.91 * |

**10 bytes is free on LongMemEval.** Not on the others (PerLTQA -0.63 pp at
11 B, RealTalk -1.69 pp). If all three must hold, 12 bytes is correct.

Degradation is smooth, so this is a **quality/space dial with a measured
price**, and below ~48 bits the `dot` scorer overtakes `hamming` (LME 80.21
vs 79.17; RealTalk 39.01 vs 37.54 at 64 bits) at **zero extra stored bytes**.

## 5. Where the cost actually is

```
BUILD  per archive (TF-IDF 1.04 s + SVD96 3.81 s)      4.85  s
SCORE  one query against a whole archive             0.008  ms
```

**Build is ~600,000x the score.** Every byte-level result above lives in
0.0002 % of the compute, and build is identical for every arm.

Scoring, real archive sizes (~500 docs), single-threaded:

| arm | stored width | index RAM | ms/query |
|---|---|---|---|
| float96 | 768 B/doc | 0.399 MB | 0.008 |
| sign_naive (today's `lib_b8`) | 12 B code, float compare | 0.395 MB | 0.071 |
| sign_u32 (12 B, 3 x uint32) | **12 B/doc** | **0.006 MB** | 0.015 |
| sign80_u32 (10 B stored) | **10 B/doc** | 0.005 MB | 0.015 |

**RAM 64.7x smaller at every scale** (77.6x at 10 B). The CPU picture went
through two corrections and is stated here in its final form:

- The first measurement used a 12 x uint8 layout and reported packed as ~3x
  SLOWER than float. **96 bits is exactly 3 x uint32**, so the same row can be
  viewed as 3 elements with *no padding*; that alone takes the ratio from
  0.30x to 0.62x on LME. A uint64 view is marginally faster still but needs
  16 B/doc — **+33 % RAM**, which defeats the point, so it is rejected.
- `lib_b8`'s Hamming arm compares against the *float* matrix, so in production
  today the byte budget buys neither the RAM nor the speed.
- With a compiled binary index the loss reverses entirely — see §11.

Totalled over **every archive of all three benchmarks** (`COSTFULL.json`,
packed popcount verified equal to the frozen scorer on all of them):

| | PerLTQA | LME | RealTalk |
|---|---|---|---|
| archives / queries | 30 / 8,265 | 470 / 470 | 10 / 705 |
| float96 index | 9.54 MB | 179.73 MB | 6.94 MB |
| sign_packed index (12 B) | 0.15 MB | 2.78 MB | 0.11 MB |
| sign80 index (10 B) | 0.12 MB | 2.32 MB | 0.09 MB |
| RAM ratio | 64.7x | 64.7x | 64.7x |
| CPU ratio, uint8 layout (superseded) | 0.34x | 0.30x | 0.31x |
| CPU ratio, uint32 layout (12 B, no padding) | **0.55x** | **0.62x** | **0.71x** |
| build total | 2.4 min | 38.0 min | 0.8 min |
| score total | 0.250 s | 0.014 s | 0.030 s |

Three things this settles:

- The 64.7x RAM win is **identical across corpora** — it is arithmetic
  (768/12), a property of the representation, not an empirical finding, and
  should not be reported alongside measured timings as though it were one.
  The CPU ratio is *not* corpus-identical once measured properly (0.55–0.71).
- **WITHDRAWN: "10 bytes is faster as well as smaller."** That was an artifact
  of the uint8 layout, where 10 B was 10 elements and 12 B was 12. Under the
  uint32 layout both 80 and 96 bits are 3 words and score at the same speed.
  **10 bytes is a RAM win only** (77.6x vs 64.7x), and §4 already prices its
  quality cost. The deletion win pays on two axes, not three.
- Build amortizes over queries per archive, and the corpora differ wildly:
  LME has 1 query per archive (worst case, build/score = 163,000x), PerLTQA
  has 275 (best case, 576x). Scoring would only equal build at ~161,000
  queries per archive, so **build dominates everywhere** — but by a margin
  that spans three orders of magnitude, and any latency claim must say which
  regime it is in.

## 6. Two findings that outrank the rest

**a. The +10 pp headline is against an unstandardized float.**
LME: `sym 54.21 - float 44.16 = +10.05` reproduces the frozen `G = +10.038`.
Standardize the same float and it becomes `55.74`, i.e. **SIGN96 is 1.53 pp
behind**. `float_std` is best or tied-best on all three benchmarks at hit@10.
It costs 768 B/doc, so it is a ceiling, not a 12-byte competitor — but the
sentence "sign quantization beats float" only holds against a weak reference.

**b. RETRACTED — "the sign code is numerically fragile" was my own bug.**

The original claim rested on rebuilding from raw text and seeing `sym` drift
86.08 -> 85.55 while `float` reproduced exactly. **The drift was a wrong
seed.** The producer uses TWO seeds and this document previously conflated
them:

```
LATENT_SEED = 5101   ->  the LSA32 stage
MIXED_SEED  = 5204   ->  the FINAL SVD96          <- the representation
```

(`v52_t4f1_beam_retrieval.py:51-54`; `v52_t4c2_centering_geometry.py:37` is
5204.) Every rebuild script here used 5101 for the final SVD96. An external
reviewer caught it; repo bytes confirm it; `audit_seed.py` settles it by
rebuilding 12 LongMemEval archives from raw text under both seeds and
comparing sign bits to the frozen cache:

```
seed 5101 :   0/12 archives bit-exact   (21.71 % of bits differ)
seed 5204 :  12/12 archives BIT-EXACT   ( 0.00 % of bits differ)
```

**The pipeline is exactly reproducible.** There is no fragility band, and the
consequence drawn from it — that R8 +0.11 pp, sign88 -0.28 pp and
`b8 - sign88` +0.90 pp sit inside a noise band — **is withdrawn**. Those
effects must be judged on their own confidence intervals.

**What the same measurement does show, in the opposite direction:** two seeds
of the same randomized SVD disagree on **21.7 % of all bits**, yet hit@10
moved only 0.53 pp. A fifth of the code can flip for half a point. That is
evidence the representation is **robust** to SVD basis variation, not fragile
— the inverse of what was published here. It has not been measured on the
frozen task's own metric, so it is an observation, not a verdict.

**Artifacts built with the wrong seed, and therefore NOT the production
representation:** `run_bottleneck.py`, `run_chunksweep.py`,
`run_svdopt.py::method_A`, `run_svdvalidate.py`. Their results are flagged in
place and need re-running under 5204 before any of them is cited. Everything
that reads the frozen caches instead of rebuilding — `run_hit10.py`,
`run_ksweep.py`, `run_dropsweep.py`, `run_codesize.py`, `run_costfull*.py`,
`run_faster.py` and all faiss scripts — is unaffected.

## 7. An optimization that is ready, and its catch

Z is ~500 x ~100,000: wider than it is tall, so its rank is at most N and the
whole factorization fits in an N-dimensional space. Instead of randomized SVD
on the wide side plus a 96 x 100,000 projector:

```
G = Z Zᵀ  (500x500)   ->  eigh  ->  U, S
fit_transform(Z) = U S
Zq V = (Zq Zᵀ) U S⁻¹        <- the 74.8 MB projector is never built
```

Measured: **SVD 19.2x faster, projector 74.8 MB -> 0 B**, total build 3.6x.

Catch: it is exact, and the production path is *approximate*, so they are not
the same object.

**The measured quality comparison is INVALID and must be re-run.** It scored
the exact path against `method_A`, which used seed 5101 — not the production
representation (§6b). The numbers it produced (+0.21 pp float, -1.67 pp sign
on 470 LME questions) compare *exact* against *a non-production randomized
draw*, which is not the question. An external reviewer measuring the build
side independently found 4.22x (LME panel) and 3.57x (PerLTQA panel) speedups,
consistent with the 3.6x here, but also reported that standardized-float
quality moved on their small panel — so "free for float" is not established
either. Nothing about adopting this may be decided until it is re-measured
with seed 5204 on both arms.

## 11. The compiled binary index, and what an independent audit did to it

A compiled binary index (`faiss.IndexBinaryFlat`, 96 bits) was tested in an
**isolated** environment (`venv_faiss`, faiss 1.15.0 / numpy 2.5.3). The
frozen venv was not modified and still has no faiss; the only bridge between
the two is exported `.npz` files. This matters because §6b established that
the sign code is numerically fragile, so a dependency change is a scientific
risk, not merely an operational one.

Everything in this section was then handed to an **independent adversarial
auditor** whose brief was to break the claims, not confirm them. The auditor
re-derived every number with its own `audit_*.py` code and did not import the
`run_*.py` files. Its corrections are folded in below and flagged.

**Correctness — survives, on stronger evidence than was first offered.**
The original check compared *sorted top-10 distance multisets*, which cannot
detect the index returning the wrong documents with the right distances, and
the "full vector" check covered query 0 only. The audit ran the full version:
**0 mismatches in 4,056,452 distance cells** across 90 archives / 9,020
queries, 0 label/distance inconsistencies, and — independently — re-derived
the packed codes from the float archives to confirm the bridge really is the
frozen `sym` arm (0/90 byte mismatches).

**But the index is valid for production and INVALID for measurement.**
96-bit Hamming produces heavy ties. The frozen metric breaks them uniformly
at random; faiss breaks them deterministically, by ascending internal index.
A tie straddles the k=10 boundary in **70.3 %** of queries, and the two
conventions disagree on 311 of them:

```
hit@10, frozen convention (expected value)  73.54 %
hit@10, faiss determinism                   73.95 %
delta  +0.407 pp, cluster-bootstrap CI [0.210, 0.607]
```

*Two cautions on that number.* It is a query-weighted pool across three
benchmarks and is **92 % PerLTQA by weight** — the programme forbids pooling,
and this figure should never have been computed. Per benchmark: PerLTQA
+0.440 [0.230, 0.630]; RealTalk +0.128 [-0.54, 0.81] ns; LME **-1.00**
[-3.0, 0.0]. And "311 queries flip" is the wrong phrase: 311 is the count of
queries where the two *conventions* differ, not a realized count.

**Why it drifts upward: document storage order carries signal.** This was a
hypothesis until the auditor ran the test that settles it — permute document
indices within each archive (identical codes, identical distances, identical
gold, only storage order changed), rebuild, re-measure, 60 times:

```
real storage order     +0.4073 pp
permuted order         -0.021 +- 0.074 pp     (p < 1/60, z = 5.78)
```

Ascending-index tie-breaking systematically favours gold. Two caveats: the
effect is invisible unless you condition on the 311 decisive queries (across
all 790 gold-bearing straddling buckets the mean gold rank is 0.4993, i.e.
dead uniform), and it is **document storage order** — that this order *is*
conversation order remains an unverified label on a real statistical effect.

**Speed — one figure survived, one was retracted.**

| comparison | value | note |
|---|---|---|
| faiss binary vs best numpy | **3.4x** | audit reproduced it and could not beat the numpy baseline (4 kernels tried, best 1.5 % better); at equal output shape it is 3.8x |
| faiss binary vs faiss float32 | **~1.51x** | **RETRACTED: the published 1.31x was wrong.** |

The retraction is a self-inflicted wound with a named cause: `reps` was set to
`min(nq, 60)`, and 50 of the 90 archives are LME with `nq = 1`, so half the
corpus was timed with a **single call**. That produced *bias, not variance*
(repeating one query keeps the cache warm, so the quartiles never warned), and
it depressed the LME figure by ~32 %.

**The deeper problem with both speed numbers.** The audit swept N and found a
fixed per-call Python/SWIG overhead of **~4.6 us**, which at the median
archive size (N ~ 484) is **73–78 % of the entire measured time**:

| N | float32 / binary | numpy / binary |
|---|---|---|
| 484 (our archives) | 1.53x | 3.49x |
| 4,096 | 3.10x | 4.52x |
| 65,536 | 5.86x | 5.03x |
| 262,144 | **8.20x** | 6.36x |

So both headline ratios are largely measurements of *call overhead*, and they
**understate** the 12-byte code's kernel advantage by more than 5x at realistic
corpus sizes. Neither number may be quoted without "at N ~ 500, one query per
call."

**Net position.** The CPU deficit of §5 is closed — the 12-byte code is
faster *and* 32x smaller than float32 at equal output shape, more so as the
corpus grows. But a compiled index must not be used to produce a reported
retrieval number, because its tie-breaking is not the frozen convention and
the difference is measurable.

**Also open from the audit, not yet done:** the two faiss scripts are
inconsistent (one normalizes before `IndexFlatIP`, one does not, so the float
index is not the frozen float arm — cost-neutral but untidy); and
`run_faiss_float.py` disclaims a quality comparison the programme already has,
since `HIT10.json` shows the 96-bit code beating raw float cosine on two of
three benchmarks.
